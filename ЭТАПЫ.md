# synthforge — поэтапный план работ

Документ для канала. Каждый этап: зачем, что делаем, почему именно так, и по
какому признаку считаем этап закрытым.

Смежные документы: `ARCHITECTURE.md` (решения по хранилищу и очереди),
`DESIGN_PROPOSAL.md` (слои, контракт генератора, режимы генерации).

---

## Этап 0. Хранилище и конвейер — ✅ сделано

**Зачем.** Прогон на тысячи сущностей идёт сутками. За это время гарантированно
что-то отвалится: перезагрузится сервер, оборвётся канал, кончатся токены.
Конвейер, который после сбоя начинает с нуля, при таких объёмах непригоден.

**Что сделано.**

- Клиент Nexorium, в котором известные ловушки API закрыты типами: разная форма
  тела у одиночного и пакетного создания, обязательная сортировка, запрет
  повторять `POST`, сверка пачки по `batch_id` после обрыва.
- Оперативный слой: сессии, очередь заданий, атомарный захват, возврат
  «повисших» заданий после смерти воркера.

**Ключевое решение — два уровня хранения.** Nexorium остаётся единственным
источником правды для контента. Но очередь заданий требует тысяч мелких
обновлений статуса, а одиночная правка записи в Nexorium идёт со скоростью
порядка 100 записей в минуту: прогон на 40 000 изображений потратил бы больше
400 минут только на запись «статус: готово». Поэтому служебное состояние живёт в
локальном SQLite, а в Nexorium уходит только готовый контент пачками по 250.
Потеря локального файла не теряет контент — сверка идёт по естественному ключу.

**Критерий закрытия.** Тесты: четыре конкурентных воркера на 100 заданий не
пересекаются ни разу; воркер, умерший с 20 захваченными заданиями, не блокирует
их навсегда. Оба зелёные.

## Этап 1. Исходящий доступ к API — 🔴 блокер

**Зачем.** Без этого не работает ни один ключ и ни один следующий этап.

**Что выяснено.** Проверка с сервера:

| Эндпоинт | Ответ |
|---|---|
| `api.openai.com` | 403 `unsupported_country_region_territory` |
| `api.x.ai` | таймаут, соединение не устанавливается |
| `api.anthropic.com` | 403 `Request not allowed` |
| `generativelanguage.googleapis.com` | 403 «нужен ключ» — то есть **доступен** |

На сервере исходящий доступ **не решён никак**: WireGuard не настроен,
VPN-сервисов нет, прокси в конфигах сервисов нет, у docker-демона прокси нет.
Четыре сервиса (telepathy, feed-reroll, sheriff, syndikot) выключены именно
поэтому — задачу не решали, сервисы погасили.

**Что делаем.** Выбрать и поднять один из вариантов:

1. WireGuard на зарубежный VPS, маршрутизировать в туннель только подсети
   провайдеров — остальной трафик сервера не трогать.
2. HTTP/SOCKS-прокси на зарубежном VPS, прокси задаётся переменной окружения
   только нашему сервису.
3. Вынести генерацию целиком на машину вне РФ, на нашем сервере оставить
   хранилище и интерфейс.

**Почему вариант 1 или 2, а не 3.** Генерация должна ходить в Nexorium за
контекстом (подбор персонала, проверка уникальности). Если вынести генерацию
наружу, каждый такой запрос пойдёт через внешний канал, который рвётся —
получим тот же класс проблем, но на более горячем пути.

**В коде это уже учтено:** обращение к провайдеру идёт через порт, адрес прокси
задаётся конфигом. Смена варианта не трогает генераторы.

**Критерий закрытия.** С сервера проходит тестовый запрос к обоим провайдерам с
реальными ключами, время ответа измерено.

## Этап 2. Модель данных

**Зачем.** Это фундамент: по ней строятся все генераторы, и переделка модели
после наполнения базы означает перегенерацию контента за деньги.

**Что даёт макет.** Присланный дизайн — готовая номенклатура полей, и из него
видно несколько вещей, которые надо заложить сразу:

- **Три состояния центра:** проверенный, непроверенный, чёрный список. Это не
  украшение, а рычаг стоимости: непроверенным нужен минимум контента (карточка
  в ч/б, пара полей), полный комплект — только проверенным. При 2000 объектов
  это разница в разы по бюджету.
- **Несколько отдельных галерей на объект:** комнаты, территория, групповые
  занятия, персонал. Это напрямую умножает количество изображений — главную
  статью расходов. Нужно решение, сколько галерей и по сколько кадров.
- **Длинные таблицы характеристик** на карточке — десятки параметров строками.
  Хорошо для SEO-объёма и дёшево в генерации: это структурные поля, а не тексты.
- **Фильтры листинга задают обязательные поля:** срочность и круглосуточность,
  район и метро, тип лечения, стоимость диапазоном, программы реабилитации, вид
  размещения, дополнительные услуги.
- **Рейтинг в двух видах:** звёзды в списке, процентный индикатор на карточке.
- **Отзывы, специалисты, карта, похожие центры** — отдельные сущности со своими
  связями.

**Что делаем.** Разложить на независимые сущности (места, люди, методики,
организация) и описать каждую отдельным документом в канал.

**Критерий закрытия.** Модель согласована в канале до написания генераторов.

## Этап 3. Слой моделей: два способа обращения

**Зачем.** Требование — оба способа рабочие, а не выбранный один.

**Что делаем.** Один порт, две реализации на каждый тип модели:

```
TextModel   ← прямой HTTP к API провайдера
            ← локальный агент по протоколу

ImageModel  ← прямой HTTP к API провайдера
            ← локальный агент по протоколу
```

**Почему через порт.** Если бы генераторы дёргали API напрямую, второй способ
потребовал бы переписать каждый генератор. Через порт это отдельный крейт в
слое инфраструктуры — генераторы не трогаются вообще.

**Разделение по задачам** (по указанию): тексты — Grok, токены в десятки раз
дешевле, а объём текстов огромный. Изображения — OpenAI.

**Критерий закрытия.** Один и тот же генератор отрабатывает и через API, и
через агента, переключение конфигом.

## Этап 4. Первый генератор сквозняком

**Зачем.** Получить реальные цифры вместо прикидок. Пока не измерено, сколько
стоит и сколько идёт один объект, планировать закупку изображений нельзя.

**Что делаем.** Самая простая сущность (места) от начала до конца: постановка
задачи словами → план → параметры → очередь → модель → пачка → Nexorium.
Прогон на 100 объектах.

**Критерий закрытия.** Известны: стоимость одного объекта, время, процент брака,
качество на глаз. **Это точка принятия решения по всему проекту.**

---

## Этап 5. Изображения

**Зачем.** Основная статья расходов и главный технический риск.

**Два независимых удара.**

*Стоимость.* 2000 объектов × количество галерей × кадры. При нескольких галереях
на объект счёт идёт на десятки тысяч изображений — это тысячи долларов за один
прогон, без учёта брака и повторов.

*Консистентность.* Несколько ракурсов одного здания и портрет одного человека в
разных контекстах требуют генерации по референсу, а не по текстовому описанию.
Чисто текстовые промпты дадут двадцать разных зданий вместо двадцати фото
одного.

**Что делаем.** Отдельная очередь и отдельный воркер, параллелизм — параметр
конфига (реальные лимиты API заранее неизвестны), учёт стоимости на каждом
задании, потолок бюджета с остановкой сессии.

**Критерий закрытия.** Прогон на одном объекте даёт согласованный комплект
фотографий; стоимость комплекта измерена.

## Этап 6. Уникальность относительно базы

**Зачем.** Требование: два режима — случайная генерация и генерация уникального
контента относительно базы.

**Как.** Два уровня: текстовый (не совпадают формулировки, дёшево) и смысловой
(не «тот же человек другими словами», нужны эмбеддинги). При срабатывании —
перегенерация с другими параметрами.

**Писать инфраструктуру не нужно:** на сервере уже работает vector-base
(BGE-M3, pgvector, 4 реплики), а у Nexorium есть встроенный поиск —
полнотекстовый и семантический.

Сравнение «каждый с каждым» на 10 000 сущностей — это 50 млн пар, поэтому
сверка идёт только с ближайшими соседями из векторного индекса.

**Критерий закрытия.** На выборке в 500 сущностей нет пар выше порога похожести.

---

## Этап 7. Остальные генераторы

Люди, методики. По крейту на тип — логика генерации отличается принципиально.

Деление предлагается **по логике, а не по номенклатуре**: врач, психолог и
консультант генерируются одинаково (биография, компетенции, портрет) — это один
генератор с подтипами. Здание и человек генерируются по-разному — это разные
генераторы.

---

## Этап 8. Составные сущности

Организация собирается **из уже созданного**, ничего не сочиняя с нуля: центр
для престарелых получает персонал с профильным опытом, а не случайных людей.
Механика — семантический поиск по базе, отбор кандидатов, проверка
совместимости, сборка.

Единственная жёсткая зависимость в порядке прогонов: запускается после
наполнения базовых сущностей.

---

## Этап 9. Наблюдение и управление

Первично — **наблюдение** за сессиями: что происходит, сколько сделано, сколько
потрачено, где встало. Постановка задач вторична, её можно делать по API.

Порядок: терминальный интерфейс на сервере → HTTP API → веб → десктоп.
Четыре клиента сразу для инструмента на двух человек — это месяцы до первого
сгенерированного объекта.

---

## Этап 10. Демо-лендинги

Единый шаблон карточки на техническом адресе: список объектов таблицей, клик —
готовая страница с фотографиями и персоналом. Нужен для приёмки глазами:
объект целиком оценить по строкам в базе невозможно.

## Порядок и зависимости

```
Э1 (доступ) ──┐
Э2 (модель) ──┼──> Э4 (первый генератор) ──> Э5 (изображения) ──> Э7 ──> Э8
Э3 (модели)  ─┘                          └──> Э6 (уникальность) ─┘

Э9 (наблюдение) — параллельно с Э4
Э10 (лендинги)  — после Э5
```

Этапы 1 и 2 не зависят друг от друга и делаются параллельно. Этап 4 — точка,
после которой станут известны реальные цифры проекта.

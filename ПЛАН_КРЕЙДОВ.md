# План крейдов: что за что отвечает и в каком порядке строим

Составлено по устному пояснению про невидимый слой. Первый шаг из предложенных
трёх: определить крейды и последовательность. Моделирование каждого крейда —
следующий шаг, после согласования этого.

---

# Часть 1. Невидимый слой — уточнённое понимание

## Что это

**Словарь параметров с допустимыми диапазонами значений.** Не архетипы, не
шаблоны — а вектор из 100–200 характеристик, которыми описывается личность.
Уникальность берётся из **комбинаторики**, а не из набора заготовок.

Почему не «попросить Грока сделать 10 000 уникальных консультантов»: опереться
ему не на что. Он изобретёт себе несколько кластеров и внутри каждого выдаст
вариации одного шаблона. Заранее это не проверить, а по факту — уже потрачены
деньги.

**Как заводится.** Список параметров генерирует ИИ (в обсуждении, не автономно),
диапазоны значений — тоже, с условием «человек работает в российском
реабилитационном центре». Результат **обязательно просматривается вручную**.
Параметров десятки-сотни, экземпляров — тысячи: ошибка в словаре размножится на
всю популяцию.

Это и есть **проектная документация**, которая потом накладывает ограничения на
генерирующего агента и направляет его.

## Два словаря на каждую роль, а не один

### Словарь личности

Пример для врача (наметка, полный список — на этапе моделирования крейда):

```
базовые         : возраст, пол, национальность, регион
семья           : есть/нет, состав, количество детей
образование     : вуз(ы) — один или несколько, специальность, годы,
                  повышения квалификации (раскладывается на несколько параметров)
опыт            : места работы, периоды, общий стаж
практика        : с наркозависимыми / с алкоголиками / с игроманами —
                  отдельными параметрами, а не одним полем «специализация»
                  опыт консультирования родственников
                  опыт в психиатрии
```

### Словарь внешности — отдельный вектор

Это не деталь, а вторая полноценная модель. Причина — наблюдение из реальной
практики: изображения, сгенерированные по одному текстовому описанию, выходят
«вылизанными» — идеально симметричные лица, идеально уложенные волосы,
одинаковая улыбка, куклы вместо людей.

Три базовых поправки, уже проверенных: несимметричное лицо, неидеальная
причёска, отсутствие дежурной улыбки. Дальше словарь расширяется тем же
способом — спросить у ИИ, какие характеристики отвечают за реалистичность живой
фотографии в отличие от вылизанной фотосессии, и разложить их по параметрам.

```
телосложение    : худой / плотный / полный
состояние       : уставший / бодрый, мешки под глазами, болезненный / здоровый
волосы          : ухоженные / сальные, причёска
лицо            : асимметрия, родинки, борода, морщины
одежда          : рубашка / свитер / халат — видна на портрете
```

При генерации портрета модель получает **оба вектора сразу**: кто это по жизни
и как он выглядит физически.

## Чего в словаре недостаточно: правила связности

Здесь надо добавить к сказанному одну вещь. **200 независимых параметров дадут
бессвязных людей**: врача 25 лет с 30-летним стажем, консультанта с чистотой
больше собственного возраста.

Между параметрами есть зависимости, и в устном пояснении они прозвучали сами —
«может оказаться, что у него много детей, и он специализируется на детской
психологии». Это и есть связь: один параметр влияет на распределение другого.

Поэтому невидимый слой состоит из **трёх** частей, а не двух:

1. словарь параметров,
2. допустимые диапазоны значений,
3. **правила связности** — жёсткие запреты и мягкие корреляции.

```
ЖЁСТКО (нарушение = брак, строка пересобирается):
  стаж ≤ возраст − 22
  дата_чистоты ≤ дата_начала_работы
  год_выпуска_вуза ≥ год_рождения + 22

МЯГКО (сдвигает вероятности, не запрещает):
  много детей          → выше шанс детской специализации
  бывший зависимый     → выше шанс роли консультанта, ниже — врача
  премиальный сегмент  → выше шанс учёной степени
```

Без третьей части комбинаторика даёт мусор, а не разнообразие.

## Практический момент по токенам

Все 200 параметров хранятся в базе, но **в промпт уходит подмножество** —
только то, что нужно для конкретного текста. Биографию пишем по одним, портрет
по другим. Иначе на 10 000 сущностей набегает лишний объём входных токенов.

# Часть 2. Список крейдов

## Группа А — механизм (не про предметную область)

| Крейд | Отвечает за |
|---|---|
| `param-dict` | как вообще описывается параметрическая модель: параметр, тип, диапазон, правила связности, сэмплирование, проверка инвариантов |

Этот крейд ничего не знает про врачей. Он знает, что такое параметрическая
модель вообще. Все остальные крейды описывают свои модели его средствами.

## Группа Б — общие компоненты, переиспользуемые всеми ролями

| Крейд | Отвечает за |
|---|---|
| `human-core` | общечеловеческое: возраст, пол, национальность, регион, семья |
| `human-visual` | внешность и физиологическое состояние, борьба с «вылизанностью» |

Вынесены отдельно по прямому указанию: визуальные характеристики не зависят от
того, врач это, консультант или психолог. Один крейд — один словарь внешности
на всех.

## Группа В — роли, по крейду на позицию

| Крейд | Отвечает за |
|---|---|
| `role-doctor` | врач-психиатр, нарколог: образование, практика, специализации |
| `role-consultant` | консультант: прошлое, история выздоровления, путь в профессию |
| `role-psychologist` | психолог: подход, методики, образование |
| `role-director` | руководитель центра: управленческий опыт, публичность |

**Это исправление моего прошлого предложения.** Я предлагал один `gen-person` с
подтипами — по указанию делаем отдельные крейды: «консультант — это уже не
врач, это другая позиция, другой опыт, другое прошлое». Общее вынесено в
группу Б, а не размазано по подтипам.

## Группа Г — объекты

| Крейд | Отвечает за |
|---|---|
| `gen-building` | здание: комнаты, интерьер, вместимость |
| `gen-location` | расположение: лес, река, удалённость от города |
| `gen-program` | программы и услуги: содержание, длительность |
| `gen-brand` | название, бренд, история организации |

`gen-building` и `gen-location` связаны с **ценовым уровнем**: премиальный центр
и бюджетный отличаются и зданием, и расположением. Значит нужна коммерческая
модель центра, задающая сегмент, и она влияет на оба крейда.

Программы генерируются **отдельным пулом**: делаем условные 10 000 программ, а
потом подходящая привязывается к центру. Так же, как персонал.

## Группа Д — композиция, ничего не сочиняет

| Крейд | Отвечает за |
|---|---|
| `compose-team` | команда центра: подбор персонала под специализацию, баланс состава |
| `compose-center` | финальная сборка центра из всего готового |

`compose-team` — не случайная выборка. Логика композиции: люди должны иметь
отношение к специализации центра, и состав должен быть правдоподобным по
возрасту — руководитель не 19 лет при специалистах по 50–60.

Подбор идёт через векторизацию: каждый человек представлен вектором в
vector-base, центр запрашивает подходящих.

`compose-center` — **в самом конце**, потому что состоит из всего остального.

## Группа Е — производное

| Крейд | Отвечает за |
|---|---|
| `gen-review` | отзывы выпускников о конкретном центре и его людях |
| `gen-showcase` | тексты витрины, описания, SEO |

## Группа Ж — инфраструктура

| Крейд | Состояние |
|---|---|
| `nexorium` | ✅ готово — клиент хранилища |
| `store` | ✅ готово — сессии, очередь, возобновляемость |
| `llm` | порт к текстовым моделям, две реализации |
| `imagegen` | очередь изображений, генерация по двум векторам |
| `feedback` | **новое** — аннотации и обратная связь, см. часть 4 |
| `server` / `client` | управление и наблюдение в реальном времени |

# Часть 3. Последовательность построения

```
1.  param-dict                     механизм параметрических моделей
2.  human-core + human-visual      общие словари
3.  role-doctor                    ПЕРВЫЙ СКВОЗНОЙ — на нём отлаживается всё
    + feedback + управление        строятся вместе с ним, иначе нечем отлаживать
    ─────────── точка проверки: цифры, качество, стоимость ───────────
4.  role-consultant, role-psychologist, role-director
5.  gen-building, gen-location, gen-program, gen-brand   (параллельно)
6.  compose-team
7.  compose-center
8.  gen-review, gen-showcase
```

Врач первым — по указанию. Шаг 3 — главный: на одной роли отлаживается вся
механика, включая обратную связь, и только после этого имеет смысл размножать
на остальные роли.

Пункт «feedback и управление строятся вместе с шагом 3» — принципиальный.
Отлаживать генерацию без инструмента, который показывает результат и принимает
замечания, невозможно: это будет ровно та ситуация, которой надо избежать —
запустили, получили тысячу штук, посмотрели, всё плохо.

# Часть 4. Управление генерацией и обратная связь

Отдельная часть, потому что это не «интерфейс», а рабочий инструмент отладки.

**Постановка проблемы:** генерация на старте — это не производство, а
эксперимент. Нельзя запустить миллион штук и посмотреть результат в конце.

**Что нужно:**

- запуск генерации с указанием количества;
- **наблюдение в реальном времени** — видно, как появляются новые фотографии и
  тексты, по мере готовности;
- **пауза** посреди прогона;
- **аннотации на конкретных результатах**: пометить отдельную фотографию и
  написать, что с ней не так — «фон плохой», «слишком угрюмый», «вылизанный»;
- аннотации **сохраняются в базу в привязке к результату**, а не теряются в чате.

**Зачем в базу.** Накопленные пометки — это вход для доработки пайплайна.
Замечание «все фотки угрюмые» превращается в конкретное действие: добавить в
словарь внешности параметр жизнерадостности с диапазоном. Замечание «везде
одинаковый фон» — добавить параметр фона. Без накопления это остаётся устным
впечатлением и теряется.

Получается цикл: **генерация → наблюдение → аннотации → доработка словаря →
генерация**. При должной отладке он сходится к качественной массовой генерации.
Это и есть основной рабочий режим на старте проекта.

# Часть 5. Что требует решения

1. **Кто заводит словари параметров.** Предлагается: черновик генерирует ИИ в
   обсуждении, приёмка ручная. Вопрос — в каком виде хранится словарь, чтобы
   его можно было править без пересборки: файл конфигурации, запись в базе или
   и то и другое.

2. **Правила связности** — согласны ли, что нужны как третья часть невидимого
   слоя? Без них комбинаторика даёт бессвязных людей.

3. **Сколько параметров реально.** 100–200 названо как ориентир. На практике
   стоит начать с 40–60 значимых по врачу и расширять по результатам обратной
   связи, а не проектировать 200 сразу вслепую.

4. **Программы: отдельный пул или генерация под центр?** По логике из пояснения
   — отдельный пул с последующей привязкой, как персонал. Уточнить.

5. **Блокер прежний:** с сервера недоступны ни OpenAI (гео-блок), ни x.ai
   (нет связи). Нужно решение по исходящему доступу, иначе шаг 3 не запустится.

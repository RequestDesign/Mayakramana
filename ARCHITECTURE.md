# Архитектура synthforge

Движок массовой генерации параметрического контента. Доменно-независимое ядро,
предметная область подключается через описания сущностей и промпт-шаблоны.

---

## Решение 1. Два уровня хранения

Nexorium — HTTP-хранилище документов, а не SQL-доступ. Его характеристики:

| Операция | Скорость / ограничение |
|---|---|
| `bulk create` (250 шт.) | быстро — 66 000 записей за ~2 мин |
| `export` (вся коллекция) | быстро — секунды, согласованный снимок |
| `PATCH` одной записи | **~100 записей в минуту** |
| Общий лимит | 1000 запросов в минуту |
| Транзакции, атомарный захват | **нет** |
| Повтор `POST` | **небезопасен** — создаёт дубликат |

Очередь заданий требует ровно того, чего Nexorium не умеет: тысяч мелких
обновлений статуса и атомарного захвата. При 100 обновлениях в минуту прогон на
40 000 изображений потратил бы **больше 400 минут только на запись «статус:
готово»**, не считая самой работы.

Поэтому хранилище разделено:

| Уровень | Где | Что хранит | Почему |
|---|---|---|---|
| **Оперативный** | SQLite локально (в volume) | сессии, задания, статусы, попытки, локи, токены, стоимость | тысячи мелких записей в секунду, транзакции, атомарный захват, WAL переживает падение |
| **Контентный** | Nexorium | дома, персонал, центры, метаданные изображений | система записи; отсюда читают порталы и сайты |

В Nexorium уходит **только финальный контент, пачками по 250 через bulk**.
Оперативная возня с задачами наружу не выходит вообще.

Потеря SQLite не фатальна: сверка идёт по `natural_key` против контента в
Nexorium, уже созданное не будет создано повторно.

## Решение 2. Write-once для контента

Контентные записи **никогда не обновляются точечно**. Перегенерация — это
удаление пачки по `batch_id` и вставка новой.

Причина — те же 100 записей/мин на `PATCH`: переклассификация коллекции
обновлениями заняла бы часы против двух минут на пересоздание. Побочно снимается
проблема распухания ревизий (каждый `PATCH` порождает ревизию) и неоднозначность
семантики `PATCH` (слияние или замена — документация не уточняет).

## Решение 3. Идемпотентность при неповторяемом POST

Обрыв соединения на `POST` **не означает**, что сервер запрос не выполнил.
Канал до сервера рвётся регулярно, поэтому это не редкий случай, а норма.

Каждая контентная запись несёт два служебных поля: `batch_id` (uuid пачки) и
`natural_key` (детерминированный ключ сущности). Протокол записи:

```
1. SQLite: строка batches, status = pending
2. status = inflight
3. POST .../records/bulk
4a. ответ 2xx        → status = committed
4b. ответ 4xx        → status = failed  (повтор бессмысленен)
4c. обрыв / таймаут  → status = unknown (НЕ ПОВТОРЯТЬ вслепую)
```

Сверщик разбирает `unknown` одним GET-запросом:

```
GET .../records?batch_id=<uuid>&per_page=1   → читаем pagination.total

total == expected      → пачка легла целиком      → committed
total == 0             → не легла                 → POST можно повторить
0 < total < expected   → легла частично           → DELETE by batch_id, затем повтор
```

`DELETE` идемпотентен, поэтому частичный случай разрешается безопасно.

## Решение 4. Сэмплер отдельно от LLM

Требование «верхнеуровневый промпт: 10% таких, 20% таких» **не реализуется
промптом** — модель не соблюдает распределения на тысячах генераций, она
сваливается в моду. Получилось бы 10 000 почти одинаковых биографий.

```
spec (постановка) → planner → sampler → N строк параметров → jobs → LLM пишет текст
```

`sampler` — обычный детерминированный Rust-код на `SeedableRng` (сид хранится в
сессии, отсюда воспроизводимость): раскладывает проценты по строкам, тянет имена
из справочников, согласует возраст с годом выпуска, распределяет по регионам.
LLM получает готовый набор параметров и только пишет по нему текст.

Заодно это даёт возобновляемость даром: строка задания либо обработана, либо нет.

## Решение 5. Единица работы — строка в БД, не шаг в голове агента

Многочасовой агентный цикл невозможно возобновить с середины: состояние живёт в
контексте модели и теряется при обрыве. Требования «SDK сам строит пайплайн по
одному большому промпту» и «сессия переживает перезагрузку сервера»
несовместимы. Побеждает второе.

Сессия — это таблица мелких адресуемых заданий со статусами. Агент вызывается на
каждое задание отдельно.

## Карта крейтов

```
synthforge/
├── crates/
│   ├── domain/      чистые типы сущностей, zero I/O, zero deps
│   ├── nexorium/    типизированный клиент, грабли закрыты типами
│   ├── store/       SQLite: сессии, очередь, пачки, захват, reaper
│   ├── llm/         trait Provider, реализации, роутер, лимиты, учёт денег
│   ├── imagegen/    изображения, референсы, консистентность
│   ├── sampler/     детерминированный сэмплер параметров, без LLM
│   ├── generators/  генераторы сущностей поверх sampler + llm + store
│   ├── engine/      сессии, планировщик, воркеры, сверщик, reaper
│   ├── proto/       типы протокола клиент↔сервер, шарится с клиентами
│   ├── mcpsrv/      MCP-сервер поверх store и nexorium
│   ├── server/      bin: axum API + WS + unix socket + engine
│   └── tui/         bin: ratatui клиент
```

`domain` не зависит ни от чего — это удерживает границы. `proto` шарится между
сервером и клиентами, поэтому протокол физически не может рассинхронизироваться.

## Стек

| Слой | Выбор |
|---|---|
| Runtime | tokio |
| HTTP-сервер | axum (WebSocket из коробки, экосистема tower) |
| Оперативное хранилище | SQLite через sqlx (runtime-запросы, без compile-time макросов) |
| Контентное хранилище | Nexorium REST |
| HTTP-клиент | reqwest + rustls |
| Лимиты | governor (GCRA) + tokio Semaphore |
| LLM | свой `trait Provider` поверх reqwest |
| MCP | rmcp |
| TUI | ratatui + crossterm |
| Удалённые клиенты | quinn (QUIC) + rustls + rcgen |
| Логи | tracing + tracing-appender |
| Ошибки | thiserror в библиотеках, anyhow в бинарях |
| Конфиг | figment (файл → env → CLI) |

sqlx взят **без** `query!`-макросов: они требуют живой БД на этапе сборки, что
ломает сборку образа в Docker. Используются `query_as` с runtime-строками.

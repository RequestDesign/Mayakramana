# synthforge — предложение по архитектуре

На согласование. Реабилитационные центры здесь — первая предметная область,
а не назначение платформы: ядро о них ничего не знает.

---

## 1. Луковые слои

Правило одно: **зависимости направлены только внутрь**. Ядро не знает ни про
HTTP, ни про SQLite, ни про конкретного поставщика LLM. Внешние слои реализуют
интерфейсы (порты), объявленные внутри.

```
┌──────────────────────────────────────────────────────────┐
│ 4. Оболочка        server · tui · desktop · mcp · proto   │
│  ┌───────────────────────────────────────────────────┐   │
│  │ 3. Инфраструктура  nexorium · store · llm ·       │   │
│  │                    imagegen · vectorbase          │   │
│  │  ┌────────────────────────────────────────────┐   │   │
│  │  │ 2. Генераторы   gen-place · gen-person ·   │   │   │
│  │  │                 gen-method · gen-org       │   │   │
│  │  │  ┌─────────────────────────────────────┐   │   │   │
│  │  │  │ 1. Ядро    domain · generator-core   │   │   │   │
│  │  │  │    типы, порты, ноль ввода-вывода    │   │   │   │
│  │  │  └─────────────────────────────────────┘   │   │   │
│  │  └────────────────────────────────────────────┘   │   │
│  └───────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────┘
```

Что это даёт практически: генератор не знает, что хранилище — Nexorium, а модель —
Grok. Он получает порты. Значит его можно тестировать на заглушках без сети, а
смену поставщика LLM или хранилища пережить правкой одного крейта в слое 3.

**Порты, объявленные в ядре** (реализуются слоем 3):

| Порт | Что делает | Реализация |
|---|---|---|
| `ContentStore` | запись и чтение готовых сущностей | `infra/nexorium` |
| `WorkQueue` | сессии, задания, возобновляемость | `infra/store` |
| `TextModel` | генерация текста по параметрам | `infra/llm` |
| `ImageModel` | генерация изображений | `infra/imagegen` |
| `SimilarityIndex` | «насколько это похоже на уже существующее» | `infra/vectorbase` |

## 2. Раскладка крейтов

```
crates/
├── core/
│   ├── domain/            типы сущностей, значения, ошибки
│   └── generator-core/    trait Generator, порты, режимы, спецификации
├── generators/            ← по крейту на тип сущности
│   ├── gen-place/         объекты и места: здания, территория, инфраструктура
│   ├── gen-person/        люди: биография, компетенции, внешность
│   ├── gen-method/        методики, программы, услуги
│   └── gen-org/           составные сущности: собираются из уже созданных
├── infra/
│   ├── nexorium/          ✅ готово
│   ├── store/             ✅ готово
│   ├── llm/
│   ├── imagegen/
│   └── vectorbase/
└── shell/
    ├── proto/             типы протокола, шарятся с клиентами
    ├── server/            axum API + WebSocket + unix socket
    ├── tui/               ratatui
    └── mcpsrv/            MCP-сервер
```

Готовые `nexorium` и `store` переезжают в `infra/` без правки кода — меняется
только путь и появляется реализация порта поверх существующего API.

**По какому признаку бить на крейты.** Предлагаю делить **по логике генерации, а
не по номенклатуре предметной области**. У врача и консультанта логика почти
одинаковая (человек: биография, компетенции, портрет) — это один крейт с
подтипами. У здания и человека логика разная — это разные крейты. Иначе
получится двадцать почти одинаковых крейтов, которые придётся править синхронно.

## 3. Контракт генератора

```rust
#[async_trait]
pub trait Generator: Send + Sync {
    /// Что этот генератор производит: схема, поля, целевая коллекция.
    fn descriptor(&self) -> &EntityDescriptor;

    /// Единичная генерация — одна сущность, синхронно, сразу с результатом.
    /// Нужна для отладки, предпросмотра и точечных доборов.
    async fn generate_one(&self, req: GenRequest) -> Result<Generated>;

    /// Массовая генерация — план, очередь заданий, возобновляемая сессия.
    /// Возвращает идентификатор сессии, а не результат: прогон идёт часами.
    async fn generate_batch(&self, req: BatchRequest) -> Result<SessionId>;
}
```

Разделение принципиальное: единичная возвращает результат, массовая возвращает
**сессию**. Прогон на тысячи сущностей идёт сутками и обязан переживать
перезагрузку сервера, поэтому синхронного результата у него быть не может.

```rust
pub struct GenRequest {
    /// Режим — см. раздел 4.
    pub mode: GenMode,
    /// Дополнительный вводный промпт поверх структурной спецификации.
    /// Например: «консультанты с опытом работы от 7 лет и сложной историей
    /// выздоровления».
    pub brief: Option<String>,
    /// Жёсткие ограничения, которые нельзя нарушить (в отличие от brief).
    pub constraints: Constraints,
    /// Сид: одинаковый сид даёт одинаковый результат.
    pub seed: u64,
}

pub struct BatchRequest {
    pub count: usize,
    pub base: GenRequest,
    /// Распределения по популяции: «20% возрастных», «10% с таким-то путём».
    /// Раскладываются кодом до вызова модели — см. раздел 5.
    pub distribution: Distribution,
    pub budget_usd: Option<f64>,
}
```

`brief` — мягкая подсказка, уходит в промпт. `constraints` — жёсткие рамки,
проверяются кодом после генерации. Смешивать их нельзя: модель нарушает
ограничения, сформулированные словами, и делает это молча.

## 4. Два режима генерации

```rust
pub enum GenMode {
    /// Случайная. Параметры даёт сэмплер, база не читается.
    /// Быстро и дёшево. Годится, пока база пустая или разнообразие неважно.
    Random,

    /// Уникальная относительно базы. Перед записью сущность сверяется с уже
    /// существующими; при слишком близком совпадении — перегенерация с другими
    /// параметрами.
    UniqueAgainstBase(Uniqueness),
}

pub struct Uniqueness {
    /// Что считаем «слишком похожим».
    pub level: UniquenessLevel,
    /// Область сравнения: вся коллекция / только текущая сессия / регион и т.п.
    pub scope: Scope,
    /// Сколько перегенераций допускаем до отказа.
    pub max_retries: u32,
}

pub enum UniquenessLevel {
    /// Текстовая: не должно совпадать дословно и по устойчивым оборотам.
    /// Дёшево, ловит шаблонность формулировок.
    Lexical { max_ngram_overlap: f32 },
    /// Смысловая: не должно быть «того же человека другими словами».
    /// Дороже, требует эмбеддингов, ловит однотипность по сути.
    Semantic { max_cosine: f32 },
    /// Оба сразу. Рекомендуется для людей и текстов описаний.
    Both { max_ngram_overlap: f32, max_cosine: f32 },
}
```

Смысловой уровень опирается на `SimilarityIndex`. Писать его не надо: на сервере
уже работает **vector-base** (BGE-M3, pgvector, 4 реплики), а у самого Nexorium
есть встроенный `/search` с полнотекстовым и семантическим поиском.

Сравнение «каждый с каждым» на 10 000 сущностей — это 50 млн пар, поэтому
сравнение идёт только с ближайшими соседями из векторного индекса, а не в лоб.

## 5. Что делает код, а что модель

Граница жёсткая, и это не стилистика — иначе не работает.

| Задача | Кто | Почему |
|---|---|---|
| разложить «20% возрастных» по 1000 строк | **код** | модель не соблюдает распределения на больших выборках, сваливается в моду |
| выбрать имя, возраст, регион, год выпуска | **код** | нужны справочники и согласованность полей между собой |
| подобрать существующие сущности для составной | **код** + `SimilarityIndex` | это поиск, а не сочинение |
| написать биографию, описание, цитату | **модель** | это и есть её работа |
| проверить, что результат непохож на существующее | **код** | модель не видит базу |
| проверить соблюдение `constraints` | **код** | модель нарушает словесные ограничения молча |

Итог: модель получает **готовый набор параметров** и пишет по нему текст. Она не
решает, каким быть сотому консультанту — это решено до неё.

## 6. Составные сущности

`gen-org` отличается от остальных тем, что **ничего не сочиняет с нуля**: он
собирает целое из уже созданного. Центр для престарелых должен получить
персонал с профильным опытом, а не случайных людей.

Механика: запрос к `SimilarityIndex` / `/search` по смыслу специализации →
отбор кандидатов → проверка совместимости → сборка. Поэтому `gen-org`
запускается **после** того, как наполнены базовые сущности, и это единственная
жёсткая зависимость в порядке прогонов.

## 7. Вопросы на согласование

1. **«Публичные методы для единичной генерации и для разовой генерации»** —
   формулировка допускает два чтения. Я исхожу из того, что имелись в виду
   **единичная** (одна сущность, сразу результат) и **массовая** (прогон
   сессией). Если «разовая» — это что-то третье, например одноразовый прогон
   под конкретную задачу без сохранения спецификации, надо уточнить: от этого
   зависит сигнатура.

2. **Уникальность — на каком уровне по умолчанию?** Текстовая дешевле и быстрее,
   смысловая дороже и требует эмбеддингов на каждую сущность. Предлагаю: для
   людей и описаний — `Both`, для служебных сущностей — `Lexical`.

3. **Область сравнения при уникальности** — вся коллекция, регион или текущая
   сессия? От этого зависит стоимость: сравнение со всей базой на каждой
   генерации требует векторного индекса и добавляет запрос на сущность.

4. **Дробление генераторов** — согласен ли принцип «по логике, а не по
   номенклатуре»? То есть один `gen-person` с подтипами (врач, психолог,
   консультант, руководитель), а не четыре крейта.

5. **Изображения** — инфраструктурный крейт, а каждый генератор объявляет, какие
   картинки ему нужны? Или у каждого генератора своя логика картинок целиком?
   Предлагаю первое.

6. **Блокирующее:** Gemini недоступен с российских IP сервера — из-за этого уже
   выключены четыре сервиса. Чем генерировать изображения? Это основная статья
   расходов проекта.
